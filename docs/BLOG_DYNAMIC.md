# Blogの投稿・交流機能

## 目的と範囲
2026-10-22の依頼に基づき、Blogと日記の管理、画像1枚、匿名いいね、承認制コメントと返信、Xへの共有、同じブラウザーでの返信確認、任意のメール通知を追加する。PHPは使わず、Cloudflare Workers、D1、R2を使う。読者の会員登録は作らない。以前のローカル執筆ツールのデータは自動移行しない。

## 日記と画面の改訂
- プレビュー（入力中・保存済み）は開くたびにCSSの取得URLを更新し、古いCSSキャッシュを再利用しない。日記の音楽リンクは日付の隣に置き、長い曲名は必要に応じて折り返す。
- 写真なしの日記本文は、枠の内側の幅全体を使って自然に折り返す。入力した改行・段落は維持する。写真付きの日記は既存の文字幅と背景保護を維持する。
- 日記の既存配置は維持する。各Blog記事の末尾（反応・コメント欄の下）に、小さな「日記」リンクを置き `/diary/` へ遷移できるようにする。下書きプレビューには付けない。
- 本文の太字は標準の `**文字**` に加え、`** 文字 **` のように記号の内側へ空白を入れた書き方にも対応する。表示時だけ端の空白を除き、保存本文・コード・エスケープした記号は変更しない。
- Blog一覧の写真はPCで行幅の約38%、スマートフォンでは本文幅いっぱいに表示する。スマートフォンは画像の下に日付とタイトルを並べる。画像は16:9の枠内に全体を表示し、切り抜かない。
- Blogの共有用HTMLに記事のOGPとXカード情報を出力する。概要はMarkdownの記法を除いた本文から作り、画像は登録写真、Markdown内の先頭のサイト内画像、共通OG画像の順に選ぶ。共有先側のキャッシュ更新や表示自体はサイト側で保証しない。
- Blog・日記・管理画面の配色と文字書体は共通style.cssに従う。専用の緑・生成りパレットと明朝体指定は使わない。Contactも共通テーマの背景・文字・ボタン色を使用する。
- 本文の写真は記事・日記とも本文幅と高さ38rem以内に収め、縦横比を保って全体を表示する。小さい写真を無理に引き伸ばさず中央に配置する。日記の背景写真の表示方法は従来どおり。
- プレビューは保存前から押せる。入力中の本文・写真・音楽を認証付きAPIで描画し、保存済みデータと公開状態は変更しない。既存記事の編集中も現在の入力内容を表示する。
- 2026-11-02の依頼により、記事・日記の本文はMarkdownとして保存・表示する。小見出し、太字、斜体、リスト、引用、リンク、コード、表に対応し、プレビューと公開画面で同じ処理を使う。HTMLを直接実行せず文字として表示し、危険なリンクを拒否する。通常の文章と改行も引き続き表示できる。読者コメントの本文は従来のプレーンテキストのまま。
- Blog・日記とも、管理画面の「公開」1回で未保存の編集内容を含めて公開する。公開時の追加確認ダイアログは出さない。公開中の編集内容も同じ操作で更新する。下書き保存では公開しない。初回の本番設定後は、投稿ごとのCodexへの依頼やGit操作を不要とする。
- 日記も同じ管理画面で下書き・公開できる。1日1件で、日付、文章、写真、音楽リンクを扱う。文章・写真・音楽のいずれか1つがあれば保存できる。写真は従来どおり日記の背景に使う。公開URLは `/diary/YYYY-MM-DD/`、`/diary/` は最新の公開日記を表示する。
- いいね、コメント、返信、通知は記事・日記それぞれに紐付ける。非公開日記の存在や写真を公開しない。通知と共有は日記自身のURLへ向ける。
- 本人表示はサーバーの管理者認証に基づく。公開ページのコメントフォームから投稿した場合も、管理者本人なら固定名と「本人」バッジを付けて即時公開する。読者が同じ名前を入力しても本人バッジは付かない。
- 説明文を常時並べず、必要な注意は入力時、通知の任意項目、データの扱いページへまとめる。記事は余白と文字組みを中心に、日記は写真と日付を中心にする。管理画面は一覧・執筆・コメント管理を分け、編集に集中できる配置にする。
- 読者のコメント入力欄は記事・日記とも既定で閉じ、「コメントを書く」または返信操作で開く。匿名投稿のTurnstileは入力欄を初めて開いたときだけ読み込む。返信操作は欄を開いて入力位置へ移動する。
- 日記の見出し末尾のドットと説明文を除き、日付は本文と同じまとまりの中に1回だけ表示する。他の日付は「ほかの日記」にまとめ、ほかの日記がなければ表示しない。写真全体には暗幕を掛けず、文字のある部分だけ背景を暗くする。

## 認証とデータ
- 管理画面と管理APIはCloudflare Accessで保護し、WorkerでもRS256署名、issuer、audience、有効期限、発行から24時間以内、許可メールアドレスを検証する。ヘッダーまたはAccess Cookieから受け取るJWTは同じ検証を行う。設定不足・認証基盤障害時は拒否する。
- 読者には署名付きのランダムなCookieを発行する。サーバーでは別のHMAC値を記録し、いいねやコメント所有者を判別する。氏名やメールからIDを生成しない。Cookie削除後の復元や端末間同期は提供しない。
- 変更APIはOrigin、JSON Content-Type、CSRFトークンを検証する。コメントはTurnstile検証とサーバー側の回数制限を必須にし、承認まで公開しない。いいねも回数制限とデータベースの一意制約で重複を抑止する。
- SQLは全てパラメーター化する。本文はプレーンテキストとして保存し、HTML出力時はエスケープする。利用者のHTMLやSVGは実行しない。
- 写真は管理者だけがJPEG/PNG/WebPを登録できる。容量、実際のファイル形式を検証し、ランダム名でR2に保存する。SVG/HTMLや利用者が指定した保存パスは受け付けない。
- メール通知は任意。確認メールのリンクを開き、明示操作を行ってから登録を有効化する。メールアドレスは公開APIに出さず、AES-GCMで暗号化して保存する。確認・解除トークンはハッシュで保存する。リンクのトークンはURLフラグメントで渡し、確認画面からPOSTする。
- 返信通知は公開済みの返信に限る。送信キューは返信と購読の組で重複を防ぎ、配信失敗は再試行する。送信にはResendのHTTPS APIを使用し、送信者ドメインとAPIキーの設定がない場合は新規購読を受け付けない。
- 返信は親コメントに対して一段までとする。親を非表示にすると返信も非表示となり、削除すると返信と通知登録も削除する。通知は10分ごとに最大20件を処理し、8回まで再試行する。外部サービスの重複排除期間を超えないよう、作成後23時間を過ぎた未送信メールは送信対象から外す。
- 生のIPはDBに保存しない。制限用には時間帯ごとのHMACを利用する。Cookieの有効期間は180日、未確認購読は24時間、通知キューは7日、制限記録は2時間を目安に削除する。Cloudflare側のアクセスログは別管理となる。

## 公開前の必須設定
本番は既存のCloudflare Pages `website` とGitHub main連携を維持する。Pages advanced modeの `_worker.js` に記事・日記APIを組み込み、静的ページは暗黙のASSETS bindingから取得する。ビルドは `npm run build`、配信先は `dist`。PagesにはCron Triggerがないため、今回の初回公開ではメール通知を無効にする。期限切れ記録の削除はリクエストを契機にバックグラウンドで実行し、同じインスタンスでは10分間隔に抑える。アクセスがない間は削除も停止する。SESSION_SECRET等の秘密は本番Pagesのsecretに登録する。プレビュー環境には本番DB・写真を接続しない。

1. D1とR2を作成し、wrangler.jsoncのID等を設定してmigrationを適用する。
2. SITE_ORIGIN、ACCESS_ISSUER、ACCESS_AUD、ADMIN_EMAILを設定する。同じAccessアプリケーションの対象に `/admin`、`/admin/*`、`/api/admin`、`/api/admin/*` を含め、共通のaudienceを使い、管理者本人のみ許可する。別のworkers.dev経由でもWorker内検証は省略しない。Accessのセッションは24時間以内とする。
3. SESSION_SECRETとMAIL_ENCRYPTION_KEYを32バイト以上のランダムな秘密として登録する。Turnstileの本番キーと許可ホストを設定する。メール通知を有効にする場合のみ、Resendの送信ドメインを検証しAPIキーと送信元を登録する。
4. ローカル試験、Workerのビルド、依存関係監査を実施する。その後に公開先・変更・制限を提示し、今回の内容に対する承認を得てからpush/deployする。
5. 本番で未認証の管理API拒否、下書き非公開、承認前コメント非公開、メール確認・解除、端末操作を確認する。

## 制限
Cookieは人物の本人確認ではないため、厳密な1人1いいねは保証しない。匿名コメントの表示名も本人の証明にはならない。返信の確認は同じブラウザーに限る。通知メールの配送と本番Access認証は、実際のサービス設定後の確認が必要。脆弱性ゼロを保証するものではない。

## 開発と検証
Node.js 24以上を開発・試験に使用する。本番の実行環境はCloudflare Workersであり、Node.jsサーバーを常時運用する構成ではない。

1. `npm ci`、`npm test` を実行する。
2. `npm run dev` で `http://127.0.0.1:4196/__preview/` を開く。ローカル生成RSA鍵で管理者認証を試し、メールはローカルの受信箱へ保存する。Cloudflare公式のTurnstileテストキーを使い、そのテスト応答のhostname/actionだけをローカル試作サーバーで補正する。本番Workerはテストキーを拒否する。
3. 別の端末で `npm run test:browser` を実行する。ローカルにMicrosoft Edgeが必要。操作確認用記事はローカルDBに残る。ブラウザーでの非公開・承認・返信・メール確認・解除と390px幅を検証し、`.local/review` に結果と画像を保存する。既定では外部ウィジェットだけをテスト用fixtureで代替する。`BLOG_LIVE_TURNSTILE=1` を設定すると実ウィジェットを使う。サーバー側のSiteverify検証はどちらの場合も実行する。
4. `npm run check:worker` と `npm audit` を実行する。秘密とDBは `.local/` に置き、Gitにも公開用distにも含めない。distはビルドで再生成する。

本番の静的アセットの配信先はリポジトリ直下から `dist` に変更する必要がある。現在のCloudflareのビルド設定を確認してから切り替える。記事・コメント・画像のバックアップとメール暗号化鍵の保管方法も公開前に決める。暗号化鍵を失うと登録メールを復号できない。
